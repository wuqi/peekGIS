# 矢量缓存方案

> 本文是矢量缓存的**唯一权威说明**。改策略、改格式、改参数前先读这里,不要翻代码。
> 涉及源码: `src/vt/`(v2 瓦片缓存)、`src/data/geom_cache.*`(v1.0 几何缓存)、`src/render/vt_render.*`(渲染与直读)。

---

## 1. 两套缓存系统

| | v1.0 几何缓存 | v2 矢量瓦片缓存 |
|---|---|---|
| 源码 | `src/data/geom_cache.*` | `src/vt/vt_*.{h,cpp}` |
| 落盘位置 | `cache/<sourceId>/{meta.bin, l0.bin, ...}` | `cache/vtk/<hash8>_e<srcEpsg>_d<dstEpsg>.vtk` |
| 载荷 | `float32` 原始坐标, **描边线段 + 填充三角形各存一份** | `int16` 量化格坐标, **单份** + LOD 金字塔 |
| 空间划分 | 均匀网格分桶(`render/bucketize.h`) | 四叉树金字塔,每层 `4^L` 片 |
| 层级 | 无(只有一套全精度) | 有(选层策略见 §6) |
| 适用 | 中小数据,精度无损 | 大数据/超大数据 |
| 压缩 | zstd level 3 | zstd level 3 + delta/zigzag/varint |
| 实测体积(ZCTA 33791 要素 / 5129 万源点) | **≈ 510 MB** | **26.4 MB**(L10) |

**v1.0 体积是 v2 的约 23 倍。** 根因两条:
1. `float32` 存原始经纬度(每点 8 B),没有 delta 编码,浪费了相邻点的高度相关性;
2. 同一份几何存两遍(描边用线段、填充用耳切三角形)。

> v1.0 的 float32 方案实测压缩率仅 0.24~0.29(vertices 4.58 B/源点 + triangles 5.50 B/源点)。
> v2 因为量化到格坐标后再 delta+zigzag+varint,实测 1.242 B/顶点。

## 2. 两套系统怎么切换 ★决策入口★

**核心:小数据走 v1.0(更优),大数据走 v2。** 判据是顶点估算量 `threshold_verts`。

### 2.1 打开文件时的判定顺序

`App::openFile` → `deferredOpen`(`src/app/app.cpp:1295`)按顺序判断,**先命中先返回**:

```
1. 后缀 == ".vtk"                    → openVtFile(p)              // 直接开瓦片缓存文件
2. 非 DB 连接串 && 非栅格后缀
   && tryOpenVtForSource(p)          → 命中已存在的 v2 缓存, 走瓦片渲染
3. 后缀 == ".shp" 或其他矢量          → queueVector(p)             // 进 v1.0 流程
4. 栅格后缀                          → 栅格流程
```

`tryOpenVtForSource`(`app.cpp:578`)只做**探测**,不估算规模:按 `displayEpsg` → `srcEpsg` 顺序
拼出候选缓存路径,存在即命中。**所以只要 v2 缓存存在,一定优先用它,不管数据多小。**

### 2.2 v1.0 流程内的分流(`queueVector`,`app.cpp:398`)

```
queueVector(path):
    ├─ tryAutoVtBuild(path) 成功 → return -1     // 本次不进 v1.0, 后台建 v2
    └─ 否则 → 走 AsyncLoader → GeomCache 读写 v1.0 缓存
```

`tryAutoVtBuild`(`app.cpp:598`)的四个条件,**全部满足**才建 v2:

| 条件 | 代码 | 不满足时 |
|---|---|---|
| `vt_auto_build = true` | `!cfg.vt_auto_build` → return false | 关掉开关则永远走 v1.0 |
| 没有构建在跑 | `vtBuilding_.load()` → return false | 并发串行,排队 |
| 顶点数 ≥ `threshold_verts` | `estimateSourceVerts(path, 0, 50000) < cfg.vt_threshold_verts` → return false | **走 v1.0** |
| 能读到图层信息 | `readVtLayerInfo` 失败 → return false | 走 v1.0 |

默认 `threshold_verts = 10000000`(一千万顶点)。
估算用**顺序步进采样**(最多 5 万要素外推),不是全量精确扫描 —— 为了让"开始建缓存"这件事尽快发生。

### 2.3 决策表

| 条件 | 走哪套 |
|---|---|
| 打开的是 `.vtk` 文件 | v2(直接) |
| 源文件已有 v2 缓存 | **v2**(优先,不看规模) |
| 顶点数 ≥ 1000 万 且 `auto_build` 开 | v2(后台建,边建边看) |
| 顶点数 < 1000 万 | **v1.0** |
| `auto_build = false` | v1.0(即使超阈值) |
| DB 连接串(`postgresql://` / `PG:`) | 跳过 v2 探测,直接走 v1.0 流程 |

### 2.4 为什么小数据 v1.0 更优

| 维度 | v1.0 | v2 |
|---|---|---|
| **精度** | float32 原样,**无损** | int16 量化,误差 ~半格 |
| **LOD** | 无。缩小时同样处理全部几何 | 有金字塔,粗层省大量顶点 |
| **首帧** | 读缓存命中即整层解压 → 可渲染 | 逐片按需解压 |
| **实现复杂度** | 低 | 高(选层/拓扑/直读/预算) |
| **体积** | 大(存两份 float32) | 小(量化 + 单份 + LOD) |
| **适用规模** | 中小 | 大 |

**小数据 v1.0 完胜:体积劣势在小规模下无所谓,而"无损 + 无需选层 + 无需直读兜底"是实打实的简单可靠。**
一旦变大,两个致命问题暴露:
1. **无 LOD** —— 缩放到全国视图也要处理全部顶点;
2. **体积线性膨胀** —— 实测同一份 ZCTA,v1.0 要 510 MB。

### 2.5 阈值调优

`threshold_verts` 是唯一旋钮。调大 → 更多数据留在 v1.0(简单但慢);调小 → 更多数据走 v2(快但有量化误差)。

注意 `tryOpenVtForSource` **不受阈值约束**:一旦某数据建过 v2 缓存,之后永远优先走 v2。
想改回去只能删 `cache/vtk/` 里对应文件(缓存管理窗口也能删)。

**当前默认 1000 万顶点是偏保守的**(偏向 v1.0)。
按实测:ZCTA 5129 万源点 → v1.0 510 MB vs v2 26.4 MB,这个规模明显该走 v2;
而几十万顶点的小面数据,v1.0 完全够用且更准。阈值定在千万级意味着"上千万才升级"。

## 3. v1.0 几何缓存格式

源码 `src/data/geom_cache.cpp`。布局(`cache/<sourceId>/`):

```
cache/<sourceId>/
    meta.bin      头部: magic/版本/源签名/源路径/各图层元信息(不含几何)
    l0.bin        图层0 几何载荷
    l1.bin        图层1 ...
cache/.index     每图层一条记录, 维护 LRU 与删除
```

`<sourceId> = sha1_hex(源路径 + "|" + mtime + "|" + size)` —— 源文件一改就换目录, 旧缓存自然失效。
文件夹/gdb 等目录型源:`mtime` 取最新文件 mtime,`size` 取递归求和。

### 3.1 `meta.bin`

```
"PGC3"(4) | ver=4(u32) | mtime(i64) | size(i64) | 源路径(长度前缀串)
  | layerCount(u32)
  | 每图层: srcEpsg(i32) | 名称 | minx,miny,maxx,maxy(4×f64) | 要素数 | ...
```

不含几何。范围无效(哨兵/NaN)时写前会从几何现场重算,否则读回后图层范围变 `(0,0,0,0)`,
"适配视图"会缩到原点、图层不可见。

### 3.2 `l<N>.bin` —— 分块流式格式(v2 版)

```
"PGCL"(4) | ver=2(u32) | numChunks(u64)          ← 文件头, numChunks 收尾时回填
  重复 numChunks 次:
    uvert(u64) | upts(u64) | utri(u64) | cz(u64)  ← 解压后各段字节数 + 压缩块字节数
    zstd 块: verts || pts || tris  (均为 float32, 源 CRS 坐标)
```

三个载荷段的语义:

| 段 | 内容 | 每元素 float 数 |
|---|---|---|
| `verts` | 描边线段, 每段 `(ax,ay,bx,by)` | 4 |
| `pts` | 点要素 `(x,y)` | 2 |
| `tris` | 面填充三角形(耳切), 每三角 3 点 | 6 |

**同一份几何存两遍**:描边用 `verts` 的线段、填充用 `tris` 的三角形。这是 v1.0 体积大的主因之一。

- 压缩:`ZSTD_compress(..., level 3)`
- 块大小上限 `kChunkDword = 1<<20` dword(约 4 MB/块),写入时按此切分
- **流式**:整层几何不常驻内存,边读边压块落盘;读时逐块解压回调,内存峰值 ≈ 一块
- `ver=1` 是旧的整层单块格式(无块数头),两者靠版本号区分;`ver=1` 缺 `utri` 字段 → 旧文件被校验拒绝后自动 MISS 重写
- 单段字节数上限 `kSanityCap = 1<<33`(8 GB),超限视为损坏

### 3.3 空间划分

均匀网格分桶(`src/render/bucketize.h`),网格数 `nc × nc` 覆盖整层范围。
线段按**中点**落格,点按自身落格,三角形按**重心**落格。
命中时每格即一个渲染桶,解压一格即可渲染(首帧 ≈ 一格解压时间)。

**无 LOD**:只有一套全精度表示,缩小时同样处理全部几何。

## 4. v2 文件格式(`.vtk`)

### 4.1 布局

```
[ 固定头 184 字节 ]
[ 数据段:     各瓦片的 zstd 压缩块, 按写入顺序追加 ]
[ 稀疏槽区:   仅"实际用到的槽", 紧凑连续 ]
[ 行目录:     每 (level, ty) 一条 16B 记录 ]
```

- 槽表每槽 16 B:`uint64 offset | uint32 size | uint8 valid | uint8 pad[3]`
- `offset` 是**文件内绝对偏移**;`valid=0` 或 `size=0` 表示该片未写
- **行目录条目**(`VtRowDir`, 16 B):`slotStart`(该行首槽下标) | `txLo`(首个有数据的 tx) | `count`(槽数) | `ty` | `level`
- 随机读:`rowDir_[(level,ty)]` → 槽文件位置 = `slotAreaOffset + (slotStart + tx - txLo) × 16`

#### 为什么是稀疏的(而不是每层满额 `4^L` 槽)

瓦片数据有**强空间局部性**:同一 `ty` 行内,只有一段连续的 `tx` 有数据(其余是空海/空地)。
满额 `4^L` 预留的利用率极低:

| 数据集 | Lmax | 满额槽数 | 实际片数 | 利用率 | 满额槽区 | 稀疏槽区 |
|---|---|---|---|---|---|---|
| 48 号 | 8 | 87,381 | 27,485 | 31% | 1.0 MB | **0.43 MB** |
| 55 号 | 8 | 87,381 | 31,213 | 36% | 0.4 MB | **0.48 MB** |
| ZCTA | 12 | **16,777,216** | 158,762 | **0.9%** | **256 MB** | **3.36 MB** |

ZCTA 单是 L12 一层的满额槽表就要 256 MB,而实际只用了 0.9%。整文件从 **411.5 MB → 86.2 MB**。

#### 构建期与读路径的关系

- **构建期**:槽位只记在内存(`slotsMem_`),**不写文件** —— 所以构建中的文件不含槽表
- **finalize()**:按 `(level, ty, tx)` 排序 → 分行 → 写紧凑槽区 + 行目录 → 回填头
- **读路径**:先看 `rowDir_`;为空(未 finalize)则回退到内存槽表(同实例读写)
- 跨实例读未 finalize 的文件会失败 —— 这与既有约定一致(构建期渲染端不读缓存文件,
  见 `app.cpp` 中"构建期不读缓存文件"的注释)

### 4.2 固定头(184 字节,`#pragma pack(1)`,`src/vt/vt_types.h`)

| 偏移 | 字段 | 类型 | 说明 |
|---|---|---|---|
| 0 | `magic[8]` | char | `"PEEKVT01"` |
| 8 | `version` | u32 | 当前 2 |
| 12 | `tileSize` | u32 | 粗层格网 512 |
| 16 | `pad` | u32 | 粗层扩边 10 |
| 20 | **`maxLevel`** | u32 | **最深层 Lmax** |
| 24 | `fineTileSize` | u32 | 最深层格网 1024 |
| 28 | `srcEpsg` | i32 | 源坐标系 |
| 32 | `dstEpsg` | i32 | 显示坐标系 |
| 36 | `minx,miny,maxx,maxy` | 4×f64 | 显示 CRS 下的数据范围 |
| 68 | `originX, originY` | 2×f64 | 全局网格原点 = L0 片左下角 |
| 84 | `tileW0` | f64 | L0 片边长(正方形边长) |
| 92 | `srcHash` | u64 | 源身份(路径+mtime+size 的 hash) |
| 100 | `buildTime` | i64 | Unix 时间戳 |
| 108 | `headerSize` | u64 | = 184,版本不符自动失效 |
| 116 | `dataStart` | u64 | 数据段起始 |
| 124 | `dataEnd` | u64 | 追加水位(压实后的真实末尾) |
| 132 | `slotAreaOffset` | u64 | 稀疏槽区起始 |
| 140 | `rowDirOffset` | u64 | 行目录起始 |
| 148 | `fullyBuiltLevels` | u32 | **已完整构建的层 bitmask** |
| 152 | `rowDirCount` | u32 | 行目录条目数 |
| 156 | `srcName[28]` | char | 源文件名 |

`headerSize != 172` 或 `srcHash` 不匹配 → 缓存自动失效重建。

### 4.3 瓦片数据(压缩块内)

```
originX:8 | originY:8 | epsg:4 | vertexCount:4 | ringCount:4
verts:  每顶点 (zigzag(dx), zigzag(dy)) varint     // delta 编码, 首点相对 (0,0)
rings:  ringCount × 16 B
```

`VtRing`(16 B):`type(u8) | hole(u8) | pad(u16) | firstVertex(u32) | vertexCount(u32) | polyGroup(u32)`
`type`:`0=线 1=面 2=点`。面:外环与孔环共享 `polyGroup`,`hole=1` 标记孔。

顶点是**相对本片原点的 int16 格坐标**,格距 `cell = (tileW0 / 2^L) / tileSizeAt(L, Lmax)`。

### 4.4 为什么必须有瓦片(硬约束)

顶点用 **int16**,范围 ±32767。实测 ZCTA 单环跨度就达 **43313 格 > 32767** —— 不分片根本存不下。
这不是设计偏好,是 int16 的物理限制。同时瓦片还提供:LOD 分级、视口随机访问、跨片只读可见区。

> 随机访问不再是严格 O(1):经行目录(`std::map` 键 `(level,ty)`)定位,是 O(log 行数)。
> Lmax ≤ 12 时行数 ≤ 8191,约 13 步比较,开销可忽略。收益是槽区从 O(4^L) 降到 O(实际片数)��

## 5. 构建两阶段(`buildVtCache`,`src/vt/vt_build.cpp`)

### 阶段 A —— 读源 + 逐层路由(0~50%)

一次遍历源数据,每个环**同时**路由到所有保留层:

```
for 每个环 sr:
    for L = Lmax .. 0 (降序):
        if !levelKept(L, Lmax, step): continue     // 隔层跳过
        cell = (S / 2^L) / tileSizeAt(L, Lmax)
        环 bbox 覆盖的每一片 → 裁剪 → 量化到 cell → 共线压缩 → 写入
```

- **最深层用 1024 细格**(精度 2×),粗层用 512 格
- `levelKept(L, maxLevel, step)`:`L == maxLevel` 或 `L % step == 0`(`step` = config `level_step`,默认 2)
- LRU 驻留上限 `lruVerts`(默认 1e8 顶点 ≈ 750 MB),超限淘汰最久未用片并落盘
- **快路径**:环 bbox 完全落在本片内 → 裁剪是恒等变换,跳过 GEOS(实测 GEOS 调用减少 93%)

### 阶段 B —— 拓扑后处理(50~100%)

对每个 `L < Lmax` 的保留层,逐片:
1. 建 arc 拓扑
2. 小面并入邻面(面积 < 4 格²)
3. 按 arc 抽稀(VW 容差 = 3 格)

**`L == Lmax` 不做后处理**:容差极小、抽稀几乎无效果、小面几乎为零,做它纯属浪费时间。

多线程:按行分配,默认 `hardware_concurrency - 2`,`PEEK_VT_TOPO_THREADS=N` 覆盖;< 8 片的层不启线程。

最后 `finalize()` 原地压实(丢弃 LRU 重写留下的孤儿块并截断文件),`setFullyBuilt(L)` 标记已建层。

## 6. 选层策略 ★核心★

实现在 `pickVtLevel`(`src/vt/vt_build.cpp`),由 `buildVtCache` 调用。
`levels >= 0` 时直接用配置值,跳过估算。

### 6.1 典型结构尺度(默认,`errorFactor > 0`)

```
1. 采样前 ≤50000 个要素,量出相邻点间距的 p50 分位数:
   nativeStep = median( 相邻点间距 )
2. targetCell = nativeStep / errorFactor
3. Lmax = round( log2( tileW0 / (1024 × targetCell) ) )
4. 体积安全阀(双条件, 见 6.4), 必要时往浅压
5. clamp 到 [0, maxLevelCap]
```

**判据的含义:让最深层格距 ≈ 数据的典型结构尺度。**

格距压到 p50 附近,形状轮廓就出来了;再往细存,只是把同一个源点复制到更细的
格子里 —— 不产生新信息, 但体积和构建时间按 4^L 涨。

**为什么是 p50 而不是 p10**

选层的目的是**观感**,不是几何精度。盯住"最细的 10% 段"会为了极端细节把
**全部**数据建得很深,而其余 90% 早就在浅层被量化到接近原样:

| 判据 | 48 号 | 55 号 | ZCTA | 结果 |
|---|---|---|---|---|
| p10(最细的 10%) | L8 | L8 | L12 | ZCTA 355 s / 86 MB,**屏幕上看不出比 L10 好** |
| p25 | L7 | L7 | L11 | 偏深 |
| **p50(中位, 默认)** | **L6** | **L5** | **L10** | 48/ZCTA 正好命中观感合格线 |
| p75 | L4 | L4 | L9 | 偏浅, 放大出锯齿 |

p50 是"数据的典型结构尺度"。`errorFactor` 是相对它的粗细倍率。

**实测(默认 `errorFactor=1.0` 自动估算)**

| 数据集 | 源点数 | p50 | Lmax | 最深层格距 | 人工确认 |
|---|---|---|---|---|---|
| 48 号(德州街区) | 3832 万 | 6.1 m | **6** | 20 m | 合格 |
| 55 号(街区) | 1567 万 | 9 m | **5** | 23 m | 偏浅一档(见下) |
| ZCTA(全国 ZCTA) | 5129 万 | 27 m | **10** | 34 m | 合格 |

> **层是 2 的幂,量化误差天然存在。** p50 落在哪两个 2 的幂之间,算出的层就会
> 偏深或偏浅最多一档。55 号的 p50 恰好使结果落在 L5/L6 的分界上(差 3%),规则
> 给了 L5,而人工确认 L6 合格。这是启发式的固有上限,不是公式错了 ——
> 需要时用 `max_level` 钉死(见 6.3)。

**显式钉死(优先于上面的一切判据)**

`max_level >= 0` 直接指定 Lmax,跳过采样与所有判据,体积安全阀也不压它
(只受 `maxLevelCap` 拦一道,默认 12)。CLI: `--maxlevel N`。

**经纬度 / 投影通用性**:公式在"世界单位"下算。地理坐标下 1° 的物理长度随纬度变化
(lat 向 1°≈111 km,lon 向还要乘 cos(lat)),高纬地区会算细;投影坐标(UTM/WebMercator)
本身就是米,无此问题。要做严格的米制比较,应在 `targetCell` 侧按层中心纬度换算。

### 6.2 `errorFactor` 怎么选

`errorFactor` 是**相对数据典型结构尺度的粗细倍率**(默认 1.0):

| errorFactor | 效果 | 48 号 | 55 号 | ZCTA |
|---|---|---|---|---|
| 2 | 粗 2 倍(省空间) | L5 | L4 | L9 |
| **1(默认)** | **贴住 p50** | **L6** | **L5** | **L10** |
| 0.5 | 细 1 倍 | L7 | L6 | L11 |

**「缓存干净到」怎么算**:最深层是 1024 格但按 512 像素显示 → 1 格 ≈ 0.5 屏幕像素。
放大时格子跟着变大,超过约 8 像素(≈ 2³~2⁴ 倍)出现肉眼可见阶梯。
Lmax 低 → 很快就要靠直读兜底,直读一被预算跳过就露出阶梯(这正是"锯齿"症状的来源)。

### 6.3 显式钉死层数(`max_level`)

`max_level >= 0` 直接指定 Lmax:**跳过采样与所有判据**,体积安全阀也不压它
(只受 `maxLevelCap` 拦一道,默认 12)。CLI 等价 `--maxlevel N`。

用于启发式差一档时(如 55 号 p50 落在 L5/L6 分界,规则给 L5 但 L6 才合格)。
这是**一次性设置**,不是每个数据集都要写。

### 6.4 顶点数驱动(兼容,`errorFactor = 0`)

旧策略:`|P(L)/4^L − targetVerts|` 最小的层。`estimateMaxLevel()` 是它的兼容入口。
仅在源无几何 / 采样不足时自动退回。

> **这个策略已被证明选层过浅**:ZCTA 在它下面只出 L5(格距 867 m),而源数据
> 相邻点中位间距仅 20 m —— 缓存比源粗 44 倍,放大必然锯齿。仅作兼容保留。

### 6.5 体积安全阀(双条件)

误差优先意味着可能建出很大的缓存。两个尺子**同时生效,谁先触发按谁**:

| 尺子 | 参数 | 默认 | 管什么 |
|---|---|---|---|
| 单片顶点数 | `max_verts_per_tile` | 262144 | 渲染帧耗时(一帧要处理整片) |
| 保留层总量 | `max_total_verts` | 1 亿 | 落盘体积 |

超了就往浅压一档,日志 **warn**:
`[vt] 超出体积上限(单片 N 顶点 / 总量 M), 已压浅到 Lmax=K`。

**估算校准系数 1.5**:格化计数反推比实际存储少(实测 48 号 1.59×、ZCTA 1.34×),
不校准会让安全阀误判"没超"而放行过深的层。校准后 48 号估 54.0M / 实际 53.1M(差 2%)。

> **为什么必须两个尺子(踩过的坑)**
>
> 先后试过三个版本,每个都有数据集会被误伤:
>
> | 安全阀设计 | 48 号 | ZCTA | 后果 |
> |---|---|---|---|
> | 单片 ≤ `targetVerts×4` (8192) | **L0,1 片,83 万顶点** | L9 正常 | 48 号放大后**全是洞** |
> | 只用总量(5000 万) | L4 正常 | L9 正常 | 48 号单片 9.2 万顶点 → **卡** |
> | **单片 262144 + 总量 1 亿** | **L7 正常** | **L10 正常** | ✓ |
>
> 根本原因:**三个数据集的要素密度差 20~50 倍**
> (ZCTA 3.3 万要素摊在 52° 内;48 号 66.9 万要素挤在 13° 内)。
> 任何单一阈值都无法兼顾,必须"按片"和"按总量"一起用。

## 7. 渲染与「超 Lmax 直读」

### 7.1 选层

`chooseVtLevel(scale, tileW0, maxLevel, builtMask)`(`src/vt/vt_level.h`):
`L = round(log2(tileW0 / (512 × scale)))`,clamp 到 `maxLevel`,再回退到最近的**已建层**
(处理 `level_step` 造成的层空洞)。

`chooseVtLevelWanted(scale, tileW0, cap)` = 纯期望层,不 clamp 到 `maxLevel`,用于判断是否超出缓存。

### 7.2 直读链路

期望层 > `maxLevel` 时进入直读(`vt_render.cpp:576`):

```
wantRaw = rawEnabled && !rawDisabled && !srcPath.empty() && Lw > maxLevel
  → enterRaw(): RawRegionStream::open(srcPath, layerIdx, dstEpsg, Lw, maxLevel, ...)
      · 视口区域反投影到源 CRS
      · 设 OGR 空间过滤 → 有 .qix 时走空间索引, 只顺序读命中要素
      · chunk() 按 8ms 分片投递 worker, 渐进产出瓦片
  → 预算投影(EWMA): 预测扫完必超 raw_budget_ms → 本次跳过(不判死, 放大后可能自动进)
  → dispatchRawChunk 逐块投递
  → 视口移出本遍区域 / 缩回 ≤maxLevel → exitRaw
```

**直读前提**:`RawRegionStream::open` 检查 `OLCFastSpatialFilter`。
无空间索引且整表 > 20000 要素 → 不可用 → `rawDisabled`(会话内不重试)。
所以**大表要享受直读,必须先有空间索引**——见 §9。

### 7.3 直读不是银弹

直读覆盖 `L > Lmax`。`L ≤ Lmax` 的档位完全靠缓存底图。
所以 **Lmax 选得浅 → 底图精度差 → 放大后直读没跟上/被预算跳过时就露馅(锯齿)**。
选层策略(§6)才是画质根因,直读是补充。

## 8. 配置项

`config.toml`,路径按 **exe 目录**解析,与启动工作目录无关。

```toml
[cache]
dir = "cache"
max_size_mb = 512          # LRU 预算(v1.0 几何缓存)

[vt]
auto_build = true          # 无缓存且顶点数超阈值时后台自动建 v2
threshold_verts = 10000000 # ★分流阈值: 顶点数 ≥ 此值才升级 v2, 否则走 v1.0(见 §2)
level_step = 2             # 隔层构建: 每 2 层保留一层(从 L0)+最深层; 1=每层都建
target_error_factor = 1.0   # ★选层: 最深层格距 ≈ 数据相邻点间距 p50 / 该值
max_level = -1              # ★-1 自动估算; >=0 直接钉死最深层(见 §6.3)
max_total_verts = 100000000 # ★体积安全阀: 保留层总顶点预算, 超了往浅压(见 §6.4)
max_verts_per_tile = 262144 # ★体积安全阀: 单片顶点数上限(渲染帧耗时)
levels = -1                # >=0 强制最深层, 跳过自动估算
raw_over_max = true        # 允许超 Lmax 直读
raw_budget_ms = 2000.0     # 单层单遍可见区扫描的读盘预算
```

> `raw_budget_ms` **不是交互预算**(扫描是 8ms 分片渐进,不卡界面),而是"值不值得花这么多盘读"。
> 设太小(如 150)会把有索引的大表直接判死,导致再放大也看不到原始数据。默认 2000。

## 9. 空间索引

直读和属性查询都依赖空间索引。**建索引(见 `docs/空间索引.md`):**

| 格式 | 语句 | 产物 |
|---|---|---|
| shapefile | `CREATE SPATIAL INDEX ON <图层名>` | 同名 `.qix` |
| GeoPackage | `SELECT CreateSpatialIndex('<表>','<几何列>')` | 空间索引表 |
| PostgreSQL | `CREATE INDEX ... USING GIST (<几何列>)` | GiST 索引 |

**图层右键 → 「新建空间索引」**(`src/data/spatial_index.h`,后台线程执行,结果回主线程显示)。
仅对「矢量 + 无索引 + `.shp`/`.gpkg`/PG 连接串」显示;探测结果按 (路径,源图层) 缓存,不每帧开文件。
FlatGeobuf 等无原地方案 → 不显示。

判据是**关掉重开后 `OLCFastSpatialFilter == 1`**,不是 SQL 是否返回结果集
(这类语句返回 null 属正常)。

## 11. 排错:症状 → 原因

| 症状 | 原因 | 处理 |
|---|---|---|
| **锯齿/边界呈阶梯** | Lmax 选得浅,底图格距远大于屏幕像素 | 调小 `target_error_factor`(1→0.5),重建 |
| **缓存只有 L0 / 放大后全是洞** | 选层被安全阀压到 0 | 看日志 `已压浅` 那行,调大 `max_verts_per_tile` / `max_total_verts` |
| **放大后卡顿** | 单片顶点过多(一帧要处理整片) | 调小 `max_verts_per_tile`(262144 → 65536) |
| 缓存体积爆炸 | `errorFactor` 太小导致 Lmax 过深 | 调大 `errorFactor`,或收紧 `max_total_verts` |
| **小数据却走了 v2 / 有量化误差** | 该源已有 v2 缓存,`tryOpenVtForSource` 无条件优先命中 | 删 `cache/vtk/` 对应文件(缓存管理窗口可删) |
| **大数据却走了 v1.0,卡顿** | `auto_build=false` 或顶点数未超 `threshold_verts` | 开 `auto_build`,或调小 `threshold_verts` |
| 大数据没自动建缓存 | 估算失败(`estimateSourceVerts < 0`)或已有构建在跑 | 看日志;并发时自动排队 |
| 只建到 L5,放大就糊 | 同上,`errorFactor` 过大 | 同上;或 `levels` 强制 |
| 放大无原始精度,只见粗底图 | 直读不可用(源无空间索引) | 右键建空间索引,或 `mkqix` |
| 日志 `超Lmax直读不可用` | `OLCFastSpatialFilter=0` 且整表 > 2 万 | 建索引 |
| 日志 `投影超预算` 一直跳过 | `raw_budget_ms` 太小 / 区域太大 | 调大预算,或放大后再进 |
| 缓存自动失效重建 | `headerSize != 184` 或 `srcHash` 变 | 正常:格式升级或源文件改动 |
| 缩放时明显卡顿 | 已知问题:直读 `rawTryScale` 3% 节流,缩放中反复 `exitRaw+enterRaw` | 待优化(改按期望层变化触发) |
| `int16 溢出` 相关崩溃 | 不可能——已由瓦片规避 | 若出现说明顶点未相对片原点 |
| 图层读回后不可见 / 缩到原点 | `meta.bin` 范围无效 | 正常:写缓存时会从几何重算;老缓存需删后重建 |
| v1.0 缓存体积暴涨 | 描边 + 填充存两份,float32 无 delta | 正常特性;大数据改走 v2 |
| `PGCL` 校验失败自动 MISS | `ver=1` 旧整层格式缺 `utri` 字段 | 正常:自动重写为分块流式格式 |
| `cache_max_mb` 触发驱逐 | v1.0 的 LRU 预算(默认 512 MB) | 调大 `max_size_mb`,或改用 v2 |
| PG 图层不走 v2 | DB 连接串被排除在 v2 探测之外 | 设计如此;PG 大表需手工 `vt_build` |

## 12. 实测基线

**三个数据集的当前缓存(默认判据自动估算, 稀疏槽表)**

| 数据集 | 源点数 | Lmax | 最深层格距 | 槽区 | 体积 | 单片顶点 | 构建耗时 |
|---|---|---|---|---|---|---|---|
| 48 号(德州街区) | 3832 万 | 6 | 20 m | 0.03 MB | 35.3 MB | 30,892 | 37 s |
| 55 号(街区) | 1567 万 | 6 | 10 m | 0.03 MB | 16.8 MB | 14,904 | 14 s |
| ZCTA(全国 ZCTA) | 5129 万 | 10 | 34 m | 0.23 MB | 26.4 MB | 32,867 | 26 s |

> 48/55 号的缓存是 `--maxlevel 6` 显式建的(规则自动给 55 号 L5, 偏浅一档);
> ZCTA L10 是规则自动估算的结果。

**ZCTA 选层 A/B(同要素 rec#11862, 同代码路径, 只差最深层)**

| 缓存 | 判据 | 格距 | 体积 | 原始→缓存最大偏离 | 阶梯占比 |
|---|---|---|---|---|---|
| 旧顶点数策略 L5 | `\|P/4^L−2048\|` 最小 | 867 m | 1.84 MB | 955 m | 55% |
| **当前 L10** | **格距≈p50** | **34 m** | **26.4 MB** | **34 m** | 41% |

误差降 14 倍。

**稀疏槽表(B1)的收益** —— 满额槽表 vs 按行稀疏(同一份数据):

| | 满额槽表 | 稀疏槽表 | 收益 |
|---|---|---|---|
| L12 槽区(ZCTA) | 256 MB | 3.36 MB | **76×** |
| 整文件(ZCTA) | 411.5 MB | 86.2 MB | **4.8×** |

深层(`Lmax ≥ 10`)收益最大 —— 满额 `4^L` 槽表指数增长而实际利用率趋近 0
(ZCTA L12 满额 1677 万槽, 实际只用 15.9 万片 = 0.9%)。
当前默认下 ZCTA 到 L10,槽区只有 0.23 MB;若用 `max_level=12` 钉到深层,收益依旧成立。

**同一份 ZCTA 走 v1.0 几何缓存:≈ 510 MB**(vertices 4.58 B/源点 + triangles 5.50 B/源点,zstd 压缩率 0.24~0.29)。
即 v2 L10 的约 19 倍 —— 这就是大数据必须走 v2 的量化依据。

**若"不用瓦片、也不量化"直接存原始精度**(实测压缩率,zstd level 3,样本 445 万顶点外推到 5129 万):

| 存储方式 | 字节/顶点 | 全量体积 |
|---|---|---|
| float64(源坐标原样) | 12.162 | 594.9 MB |
| float32 | 6.119 | 299.3 MB |
| int32 格 1e-4°(11 m) + delta | 0.969 | 47.4 MB |
| int32 格 1e-5°(1.1 m) + delta | 1.830 | 89.5 MB |
| int32 格 1e-6°(0.1 m) + delta | 2.889 | 141.3 MB |
| **int16 格(瓦片式)** | — | **不可能:单环跨度 43313 格 > int16 上限 32767** |

即:即使放弃瓦片改用 int32,要保住 11 m 精度也得 47.4 MB(仍是 v2 的 2 倍),且**失去 O(1) 随机访问**
(缩放时须扫全部 5129 万点)。放弃量化则退化到源文件量级(595 MB)。
**所以"不用瓦片"不是一个更省的选项,而是更贵且更慢的选项。**

**其它**

- 48 号:`.qix` 8.73 MB,构建 58.7s(GEOS 快路径 + 拓扑多线程后,原 83.3s)
- 55 号:建索引 4.1s,`.qix` 4.65 MB
- 空间过滤效果(55 号, 33k 要素, 命中 33183):无 `.qix` 3746 ms → 有 `.qix` 1279 ms

**回归基线**:`tests` 94/94(601640 assertions)、`vt_tests` 28/28(1234 assertions)。
